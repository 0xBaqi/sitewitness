# Baronal Development Method V2 — SiteWitness

User-supplied method, 3 November 2026.

1. Problem-first architecture: solve real construction-inspection problems; avoid unnecessary abstraction and feature sprawl.
2. Meaningful Meta integration: genuine Muse Spark inference; never label fixtures, manual observations or simulation as live AI.
3. Evidence-backed findings: distinguish visible evidence, uncertainty, limitations and recommended human verification. No invented SAM masks or boxes.
4. Human control: review, edit, accept, reject or investigate before finalizing.
5. Complete workflow: upload → analyze → review → save/reopen → export; prefer one reliable journey.
6. Independent verification: actual behavior, API responses, schemas, persistence, authorization, errors and browser interactions; builds alone are insufficient.
7. Security and cost: protect keys, preserve public inference gates and request limits, prevent unintended charges.
8. Professional UX: clear first-screen value, responsive design, useful loading/errors, explicit provenance and an easy judge journey.
9. Honest release evidence: distinguish implemented, locally tested, hosted-tested and unverified; no unsupported engineering-safety claims.
10. Maintainability: preserve working code and regression tests; focused commits without rushed product damage.

Gate: code alone does not complete a feature. It must work, be independently verified and serve the actual product purpose. Automated behavior verification here is distinct from independent professional review of construction conclusions; no separate human reviewer is claimed.

This release uses an explicitly identified captured live result in place of a new analyze operation, as authorized for this bounded workflow. It does not fulfill general live analysis or authenticated cloud persistence of AI reports; both remain separate release gates.
