# SiteWitness v0.5 — functional manual inspections

Baseline: `da79e08`. Date: November 1, 2026.

## What works now

The primary workflow requires no account, API key, model billing, or external storage service. Select **New manual inspection**, enter a title, optionally add a summary and inspection notes, attach up to five photographs, and add observations. Each observation has a title, human-authored description, category, evidence, limitations, reviewer decision, and reviewer notes. All observations remain human-authored after review or editing.

**Save manual inspection** retains the report and photographs together in one IndexedDB transaction. **Saved manual inspections** reopens the committed record, including photographs and review decisions after a browser reload. Removing photographs and observations takes effect on the next save. **Delete saved inspection** deletes the saved record and its photographs after confirmation. There is a 25-inspection cap; the application refuses additional records instead of silently dropping older ones. Concurrent saves use revision checks, so another tab's edits are not overwritten silently. Unsaved changes are identified, navigation within the workflow requests confirmation, and browser unload protection is installed while a draft is dirty.

**Export manual JSON with photographs** exports the current draft, including unsaved changes, human-authored provenance, observation/review metadata, and each original photograph as a data URL. Export does not imply that browser save succeeded. This is a portable JSON archive, not a PDF report, and there is no archive import UI in this milestone. Store exports securely; clearing browser data, changing origin/profile, or losing the device can lose the browser copy.

Manual photographs never leave the browser. Validation checks MIME allowlist, byte size (1 byte–4 MiB), matching JPEG/PNG/WebP signatures, successful browser decoding, and a 24-million-pixel ceiling. Each inspection holds at most five photographs. Original files, including metadata and any animation, are retained; this is not image sanitization or a forensic image validator. Large/deceptive images still cost local decode resources. Existing stricter server analysis-image validation remains in place, although live analysis is locked off.

## Provenance and legacy compatibility

Types and schemas distinguish `manual`, `ai` (with model identity), and `legacy_unknown`. Manual records have no model identity. New manual exports repeat their origin explicitly. The analysis handler emits AI provenance only from its isolated inference path, which remains locked in production and tested using synthetic stubs only. There is no live Analyze button and no automatic generation of observations.

Existing browser-local records without provenance are read as **Legacy record · origin unverified**; they are never retroactively asserted to be AI output. Their photograph restoration, review, notes, and JSON exports remain available below the manual workspace. Manual records use a separate, versioned browser database; legacy data is not silently migrated or overwritten.

The authenticated server POST schema now requires manual provenance and supports human review metadata and inspection notes. It rejects client claims of AI generation, unknown origin, extra ownership fields, photographs, and invalid review references. This deliberately tightens the v0.4 write contract. Existing encrypted records remain readable; records with no provenance are labeled unknown in API responses. New human records receive the fixed human-authored notice. Server records still have separate server-generated IDs, seven-day expiry, and existing caps. The browser UI does **not** synchronize to this API in this milestone, and the API still does not retain photographs. Browser and server deletion are separate operations.

## Authentication and persistence assessment

The existing encrypted backend protects records with AES-256-GCM and authenticated owner/ID/expiry metadata. Stable user IDs are resolved from server-configured hashes of high-entropy bearer tokens. Queries and deletion constrain ownership. Revoked tokens fail subsequent requests. Cross-origin requests, malformed credentials, unsafe storage paths, oversized data, and storage failures are rejected. Tokens and encryption keys are not provided to browser bundles. The inference code lock and durable zero-default call allowance remain unchanged.

This is a foundation for a controlled single-host API, not a complete identity system. Manual credential provisioning, global request caps, no refresh/session management, no UI login, no independent key rotation/recovery, and lazy expiry purging remain. Local browser storage is **not** encrypted by the application or separated by user accounts: everyone with access to the same browser profile can read it. Browser contexts/profiles are the relevant boundary. Do not describe the browser workspace as authenticated multi-user storage.

### Recommended architecture

For the present no-spend workflow, keep the application on the existing machine for non-sensitive manual inspections, with exports as user-managed backups. This is implemented and requires no infrastructure provisioning.

For a future controlled private pilot, the smallest extension to the existing backend is a single Node 24 host with a persistent local disk, HTTPS, authenticated UI, encrypted image storage with owner-scoped access, and tested encrypted backups plus independent key recovery. Keep the SQLite file outside the checkout and web root; preserve it across releases. Never mount it on an untrusted/network filesystem or ephemeral serverless storage. SQLite's own guidance supports application-server databases on the same physical machine, while recommending client/server databases for many clients accessing the database over a network. [SQLite guidance](https://www.sqlite.org/whentouse.html).

For a public, cross-device product, the safer design is managed authentication plus Postgres ownership policies and private object storage. A candidate is Supabase Auth/Postgres/private Storage with a separately approved frontend host. Every record and photo path must be scoped to the authenticated user's ID, checked for read/write/delete, and covered by negative cross-user tests. Private photo downloads should use bounded authorization, and uploads require validation, quotas, cleanup, and a retention policy. Service-role credentials must never reach clients; encrypted report payloads would also need a documented key-management design. This is an architectural recommendation, not implemented or provisioned integration. [Database row security](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

At research time, Supabase lists a $0 plan with 500 MB database storage, 1 GB file storage, and 5 GB egress, and states that free projects pause after one week of inactivity. These constraints make it a candidate for an approved limited pilot, not an availability or permanent zero-cost guarantee. Check account eligibility, current terms, photo volume, backup requirements, and upgrade behavior before provisioning. No account or project was created. [Current pricing](https://supabase.com/pricing).

Vercel cannot make the current local SQLite database durable; its serverless filesystem is ephemeral. Keep server persistence disabled there. A Vercel preview can show browser-local manual functionality, but that is not cloud backup or account-based persistence. The existing preview restrictions and noindex header remain, and noindex is not access control. [Vercel SQLite support](https://vercel.com/kb/guide/is-sqlite-supported-in-vercel).

## Mobile, accessibility, and failure behavior

The manual workflow uses labeled native inputs, a fieldset disabled during asynchronous operations, 44px minimum buttons, keyboard focus outlines, focus placement for new inspections/observations, live save-status messages, alert errors, and a responsive photo grid. A 375px browser test exercises keyboard save, image removal, deletion, and horizontal-overflow checks. Tests cover corrupt legacy history, missing legacy photos, upload rejection, save failures retaining drafts, and concurrent editing conflicts. This is a focused Chromium/keyboard/mobile-viewport assessment, not a complete WCAG, screen-reader, or physical-device certification.

Browser storage can be unavailable, blocked, damaged, evicted, or full. Failures must not be presented as successful saves. Invalid stored manual data is not overwritten automatically. Export is available for an open draft even after a save failure. Large photo archives consume memory and disk; no background sync, offline application installation, restore wizard, or backup automation is provided.

## Verified results

The final code passed **46 backend tests and 12 browser tests**, typecheck, the production build, npm audit (zero vulnerabilities), and diff checks. A scoped exact-value credential and synthetic-fixture scan covered 37 tracked/unignored paths and 38 production JavaScript files with no findings. Secret values were not printed. This is not a general penetration test or exhaustive secret-history audit.

All 43 prior backend tests remain, with three added provenance/revocation cases. Legacy restoration/review/export, missing-photo, corrupt-history/mobile, and disabled-API coverage remain. The obsolete AI-submit UI test was adapted to the visible unavailable/manual state; new manual save-failure and busy-state tests cover the replacement interaction. Browser assertions and timeouts were not weakened. Early runs found selector ambiguities, which were corrected; a later resource-sensitive timeout did not reproduce in the final full run. The complete manual journey passed in 5.1 seconds in that final run.

No package dependencies were added. No Meta request, paid resource, push, or deployment occurred. Node 24.21.0 and local Chromium were used. The mobile screenshot contains only synthetic test data.
