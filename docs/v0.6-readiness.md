# v0.6: private inspection snapshots (controlled pilot)

Baseline a0a4518. November 1, 2026. No deployment, push, purchase or model call authorized or performed.

## Product decision and honest scope
Extend the existing Node 24 + encrypted SQLite implementation on one durable host. No additional service, dependency, credit card or model billing is needed to run on the existing machine. This does not supply a free public production host. Public deployment requires approval, HTTPS, a persistent disk, an operator and monitoring. Vercel serverless is unsuitable for this local database: https://vercel.com/kb/guide/is-sqlite-supported-in-vercel .

Managed authentication/database/private object storage remains the better public self-service direction, but it adds provisioning and operational dependencies. Supabase free projects require operator-managed off-site backups, and database backups exclude storage objects: https://supabase.com/docs/guides/platform/backups . Do not assume a free plan supplies durable photo backups or guaranteed availability. Recheck plan eligibility and limits before any provisioning. No paid-host recommendation or permanent zero-cost promise is made.

## Working journey
The main page now states the manual inspection steps and links to /vault. Create, photograph, record observations, review, save and export JSON with photographs. In /vault, enter an individually issued access token, connect, and upload the export. On another browser/device, connect with the same token and restore a snapshot. Restoration creates a new browser-local ID, so it cannot overwrite an existing local inspection. Delete removes the server snapshot, including photographs, in one database operation. Local copies and independent backups remain separate.

This is explicit snapshot transfer, not automatic synchronization. Editing a restored copy requires another export/upload. Login is personal bearer-token access, not passwords, signup, MFA, account recovery or a session-cookie system. Tokens stay in page memory and never enter browser storage. Reload clears them. A holder of a token can access that account; the operator revokes it by removing/changing its hash in SITEWITNESS_USERS. HTTPS and safe token delivery are mandatory outside localhost. Browser restores use the existing shared-profile IndexedDB; disconnect does not erase those copies.

## Storage and security
Use the existing INSPECTION_STORAGE_ENABLED, SITEWITNESS_USERS, SITEWITNESS_STORAGE_KEY and SITEWITNESS_DATA_DIR configuration described in v0.5. Set SITEWITNESS_PUBLIC_ORIGIN to the exact HTTPS public origin (scheme and hostname, no trailing slash), especially behind a reverse proxy. Never derive it from forwarded request headers. Keep the data directory outside the checkout and served directories, operator-owned with mode 0700, database mode 0600. Never use ephemeral or network-mounted disk. Serverless hosting fails closed.

Archives validate exact manual provenance, metadata, photo identity/order/count, canonical base64, byte counts, format, successful image decode and the 24-million-pixel limit. Five photographs, each at most 4 MiB; request limit 28 MiB. Original metadata is retained. Reports and photographs are encrypted together using existing authenticated encryption and owner/ID/expiry binding. User-controlled ownership and AI-origin claims are rejected. Authentication, cross-origin rejection, revocation and global request limits apply. No public photograph URLs exist.

Encrypted serialized content is capped at 40 MiB per owner and 128 MiB globally, alongside existing record caps. These are logical content limits, not filesystem-size or memory limits. Base64 overhead means a maximum-size inspection can consume most of a user's quota. Snapshot reads currently load all of an owner's records; pagination and concurrency controls are public-scale blockers. Global rate limits can cause one user to deny service to others. Inference remains code-locked off.

Snapshots expire seven days after upload. Reads/writes purge expired records; expiry is not yet a scheduled physical-erasure service. Deletion cannot erase backups or browser copies. Re-uploading creates another snapshot with a new retention period. Before sensitive use, agree metadata handling, residency, retention and backup deletion policy.

## Backup and recovery runbook (operator-owned, not automated)
1. Stop all SiteWitness processes using the database, including maintenance jobs. Confirm they are stopped. The store uses DELETE journaling and FULL synchronous writes; never copy a live database using this procedure.
2. Copy the complete sitewitness.sqlite file to a restricted off-site destination, with no web access. Retain the 32-byte encryption key separately in an approved secure location. Losing the key loses the data; co-locating it with a backup defeats that separation.
3. Restore into a new restricted data directory while the application is stopped, preserving the original backup. Set the recovered key and current user-hash configuration, then start an isolated instance. Authenticate as two distinct users; verify the owner's report and photographs, absence for the other owner, and deletion. Expiry timestamps are retained, so an expired snapshot must remain unavailable.
4. Before returning a restored database to service, reconcile deletions since backup. An old backup can otherwise resurrect a deleted but unexpired record. Rotate/revoke compromised credentials. Keep a deletion ledger and apply a documented backup retention policy before admitting sensitive pilot data.

An automated test verifies closed-database copy/restore, encryption-key failure, owner separation and expiry. It is not evidence of off-site disaster recovery, scheduled backups or key recovery in production. Backup automation, deletion reconciliation and an actual operator recovery drill remain deployment gates.
