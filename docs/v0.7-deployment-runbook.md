# v0.7 single-host controlled-pilot deployment runbook

Status: configuration prepared locally; NOT deployed or host-certified. No spending or provisioning authorized. Retain manual inspections and explicit human provenance; inference stays disabled. This is an operator-managed pilot, not public self-service.

## Architecture decision
One Linux host, one Node 24 Next.js production process, local durable block disk, encrypted SQLite, systemd supervision and expiry timer, HTTPS nginx reverse proxy. Keep records and original photographs together in authenticated AES-256-GCM envelopes. Preserve owner/ID/expiry binding and current quotas. No network-mounted SQLite, ephemeral/serverless filesystem, replicas, shared public token or automatic scaling. Disk persistence is not an off-site backup. No hosting plan or zero-cost guarantee is implied.

The checked-in templates are under deploy/. They are not installed or enabled by tests. Node 24 and all locked npm dependencies (including tsx for maintenance) must be installed before launch. No new dependencies were introduced. The self-hosting guidance recommends a reverse proxy: https://nextjs.org/docs/app/guides/self-hosting . Timer semantics: https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html . Validate against the actual host versions before installation.

## Prepare after separate launch approval
1. Assign an operator, approved host/region, domain, durable local disk, disk capacity alert, patch policy, time synchronization and HTTPS certificate renewal. Firewall ingress to HTTPS and restricted operator administration; never expose port 3000. Disable platform disk snapshots until their retention/deletion policy is agreed.
2. Use a dedicated non-login sitewitness account. Install the selected Node 24 runtime at /opt/node24/bin/node. Build the verified commit with `npm ci`, `npm run typecheck`, `npm run build`. Do not inject production secrets into builds. Put the release at /opt/sitewitness/current, owned by the operator and read-only to the service account, except .next/cache. Create .next/cache before starting units.
3. Create /var/lib/sitewitness owned by sitewitness, mode 0700 on the persistent disk. Keep it outside releases, static files and proxy roots. Database mode is 0600. Application quotas limit serialized records, not filesystem space. Provision headroom for SQLite journal, releases and recovery staging.
4. Copy deploy/sitewitness.env.example to /etc/sitewitness/sitewitness.env, root-owned mode 0600. Supply a cryptographically random 32-byte key encoded as 64 hex characters. Keep an independently protected recovery copy. Generate independent random 32-byte base64url bearer tokens for each person; store only SHA-256 hashes in SITEWITNESS_USERS. Transfer tokens privately; never paste them into logs, tickets or command history. Stable user IDs must never be reassigned to another person.
5. Set the exact HTTPS public origin without trailing slash. No NEXT_PUBLIC secrets. Remove VERCEL. The units override inference and model credentials to disabled/empty. Copy service/timer templates into systemd only after reviewing paths, ownership and restrictions. Validate with `systemd-analyze verify` on the target host. Start the service and expiry timer; check service status, timer scheduling and journal. Do not interpret installation as a passed smoke test.
6. Adapt nginx.conf.example with the real hostname and certificate. Validate with `nginx -t`. The template intentionally has no plaintext HTTP listener: use a separately reviewed certificate renewal/redirect setup. Keep request/response bodies and Authorization out of logging, disable API caching, and avoid proxy disk buffering of private photographs. Confirm upstream bound only to loopback. Validate 28 MiB uploads and slow-request limits through HTTPS.
7. Test with synthetic accounts and photographs first. Exercise manual creation/export, two-user separation, upload, browser restoration with visible photo, restart durability, revocation after restart, deletion after restart and timer-driven expiry. Test from a second device. Confirm HTTP fails, foreign-origin writes fail, API responses say no-store, credentials never appear in client assets, and no Meta requests occur. Purge synthetic data afterward.

## Access and retention contract
Access is possession of an individually issued bearer token; there is no signup, MFA, password reset or account recovery service. Anyone with a token has the same rights as its owner. Revoke by removing/changing its hash and restarting the service. Keep the user ID stable during token rotation. Local browser copies belong to that browser profile; disconnect/revocation/server deletion does not erase them. Browser tokens stay in memory only. Export/upload is explicit snapshot transfer, not synchronization.

Each snapshot expires exactly seven days after upload, not seven days after last read. Reads cannot retrieve expired snapshots. Re-upload creates a new record and clock. The new `npm run storage:expire` command purges expired rows without traffic; the timer runs every five minutes with up to 30 seconds scheduling accuracy. This is a cleanup target while the host is healthy, not an exact physical-erasure deadline. Persistent timers catch up after downtime. Monitor failures and alert if no successful cleanup occurs for 15 minutes. Secure-delete overwrites SQLite deleted content; it does not prove erasure from SSD blocks, host snapshots or backups. Maintain accurate host time. User deletion affects the primary database only; separate exports/browser copies remain.

## Backup, recovery and deletion gate
Automated off-site backup, a durable deletion ledger and host recovery drill remain launch blockers for sensitive pilot data. Do not enable unattended snapshot backups and claim deletion compliance. Decide retention, residency, key recovery and deletion policy first.

For an operator-supervised recovery drill: stop the application AND expiry timer/service; confirm neither uses the database; copy the closed database to a restricted off-site destination and checksum it. Keep the encryption key separate. Never copy a live SQLite file with an ordinary filesystem copy. Preserve the source backup. Restore into an isolated restricted directory using the original key and CURRENT user hashes. Before reopening service, reconcile every deletion since backup against an independently retained operator deletion ledger, or discard all restored snapshots if completeness cannot be proven. Run cleanup before exposing the restored instance. Never reset expiry timestamps. Test correct-owner photograph restoration, other-owner denial, revoked-token denial, expired-record absence, wrong-key failure and deletion. Only then approve returning it to service. The app does not yet maintain that external ledger automatically.

For rollback: stop service and timer; preserve a closed-database backup; switch the application release only after checking schema compatibility; retain current credentials/key/data. v0.7 introduces no schema change. Do not roll back the database blindly: it can resurrect deleted snapshots. If key loss, compromise or unexplained storage errors occur, stop access and investigate; never silently replace a database or key.

## Local validation and outstanding limits
Run `npm run test:backend`, `npm run typecheck`, `npm run build`, `npm run test:smoke`, `npm run test:browser`, `npm run test:vault`, `npm audit`, and `git diff --check`. Smoke uses only synthetic secrets, a temporary disk and a local production server on port 3119. It checks restart persistence including actual PNG bytes, ownership, revocation, deletion, no-store, foreign-origin rejection and cleanup with no request traffic. Existing browser tests exercise real upload/restore, visible photographs and the manual workflow. Existing offline backup tests cover recovery, wrong key and expiry. These do not prove TLS, systemd scheduling, reverse-proxy behavior, off-site recovery, power-loss safety, disk exhaustion or human acceptance on the chosen host.

Retain the v0.6 limits: all owner records load together, global rate limits permit denial of service between users, limited quotas, no organization roles, self-service accounts or automatic sync. Public-scale rollout needs pagination/concurrency/load work and a stronger identity system. Meta billing/access, genuine model evaluation and SAM remain blocked and unverified; no synthetic inference output is introduced.
