# SiteWitness private HTTPS preview: rollout decision and checklist

Prepared 2026-11-01 (Africa/Lagos), starting at clean commit 44ddf5f. Preparation only: no purchase, push, DNS change, provisioning, deployment or model call authorized or performed. Read together with v0.7-deployment-runbook.md and v0.8-recovery-runbook.md. This document supersedes the unrestricted proxy setup for this private preview.

## Proposed decision

One operator-managed Linux x86-64 VM, Node 24, one Next.js process, nginx TLS, systemd expiry timer, encrypted SQLite at /var/lib/sitewitness on the VM's persistent local disk. No autoscaling, replicas, network-mounted database or serverless storage. Start with 1-3 invited testers, non-sensitive construction photos or synthetic images, and independently saved exports. This is a manual-inspection preview; Evidence Trace with Meta is not working or verified yet.

Recommend DigitalOcean Basic Regular 2 GiB / 1 vCPU / 50 GiB at $12/month compute, subject to account availability and checkout confirmation. Memory adequacy must be measured; do not silently resize or spend more if the build fails. A compatible isolated Linux build machine can prepare the release without production secrets. Keep at least 5 GiB free at launch and alert at 80% disk usage or under 2 GiB free. Persistent disk survives process/release restarts; it does not survive every host failure or deliberate VM deletion.

## Configuration and access

- deploy/nginx.conf.example now requires /etc/nginx/sitewitness-preview-allowlist.conf. Copy the checked-in example: it denies everybody until approved public tester IPv4 addresses are added above deny all. Keep root ownership, mode 0644, no untrusted writers. nginx checks rules in order: https://nginx.org/en/docs/http/ngx_http_access_module.html . An absent include must fail nginx validation.
- This gate covers the workspace, assets, vault and API. It identifies a network, not a person: people sharing an allowed IP can open the workspace. Private snapshots still require independent random bearer tokens, stored as hashes with stable user IDs. Do not share tokens. Do not add HTTP Basic Auth, which would compete with the API's Authorization header.
- Use direct DNS to the VM, with no CDN or forwarded-IP trust. Do not add allow rules inside locations, which can override inherited rules. Mobile IP changes require operator review, nginx -t and reload. Never solve lockout with allow all or a broad carrier CIDR. If roaming access is essential, select an identity gateway as a separate reviewed change before deployment.
- Initial proposal: IPv4-only DNS A record, no AAAA record, HTTPS 443; firewall 22 to operator IP and 443 to tester IPs, default deny other ingress. Port 3000 stays loopback-only. Match firewall and nginx ACL. Check provider console recovery access before restricting SSH.
- Use a hostname you control and a valid certificate, with DNS-01 issuance/renewal so the template needs no public port 80. Configure a supported ACME client after choosing the DNS provider; store any scoped DNS credential root-only. Test renewal and reload, alert 14 days before expiry. Domain and DNS changes require approval; certificate issuance publishes the hostname in certificate transparency.
- TLS 1.2/1.3, no-referrer, noindex and frame denial are prepared. noindex is advisory, not access control. Access logs are off; never enable debug or log request bodies/Authorization. No proxy upload buffering or response disk buffering. Inspect actual host error logs for metadata exposure.
- /etc/sitewitness/sitewitness.env: root-owned 0600. /var/lib/sitewitness: service-owned 0700, database 0600. Use the existing env example with the actual exact HTTPS origin, independent random 32-byte storage key and per-person token hashes. Keep key recovery separately protected. Never copy .env.local to the host or build with it. Inference flag false, call limit zero, model key/access code empty. Units also override flags and credentials. Existing route has no inferenceAuthorized opt-in.
- Release files are operator-owned, service read-only except .next/cache, data outside releases. Install all locked dependencies including maintenance tools. Do not run npm audit fix or update dependencies as part of deployment. Confirm no inherited VERCEL setting. Use trusted time synchronization.

## Concrete rollout checklist (after explicit approval)

Record operator, timestamp, release hash, host/region, domain, approved budget, tester IDs/IPs, off-site destination and evidence location. Never record tokens or encryption keys in this checklist.

1. Confirm provider checkout and budget including taxes/overages, disk lifecycle and region. Provision only the approved plan; turn provider snapshots/backups off until their retention policy is accepted. Set billing alerts; alerts are not hard spending caps.
2. Prepare patched Linux host, operator SSH key, non-login sitewitness account, Node 24 at /opt/node24/bin/node and nginx. Verify host clock, firewall and persistent filesystem with findmnt -T /var/lib/sitewitness; record volume identity, filesystem type and free space. No temporary filesystem. Ensure mount failure cannot result in writes to an unintended fallback directory.
3. Transfer only tracked files for the validated commit through an approved method. No push is implicit. Install locked dependencies and build without production .env files. Set /opt/sitewitness/current to the verified release, create writable .next/cache and restricted data directory. Record node/npm versions and commit.
4. Install protected environment file, storage key and current user hashes. Copy systemd units and allowlist. Configure the selected DNS name, DNS-01 certificate/renewal and nginx host/certificate paths. Run systemd-analyze verify on the actual units and nginx -t. These host-specific checks are mandatory even if local tests passed.
5. Start one application process and enable expiry timer. Check systemctl status, list-timers and successful cleanup journal entries. Verify ss shows only 127.0.0.1:3000. Confirm the service cannot modify release source files or read protected home directories. Confirm timer is enabled and catches up after reboot.
6. From an allowed network verify certificate chain/hostname, HTTPS workspace and vault, no mixed content, and no plaintext HTTP access. From a disallowed network verify denial for /, /vault, static assets and /api/archives (403 or firewall rejection); test forged X-Forwarded-For cannot bypass it. Test the VM's direct address and alternate Host headers cannot bypass restrictions through another virtual host.
7. On approved HTTPS origin, verify missing/wrong token returns 401; valid token works; foreign Origin and Sec-Fetch-Site cross-site return 403; private API responses have Cache-Control: no-store. POST /api/analyze must return 503 disabled without contacting Meta. Confirm no model key is present and no external model requests in the test journey.
8. Two synthetic accounts: create manual inspection with real non-sensitive photo bytes, save/export including photo, upload archive, view only own snapshots, restore on a second device and visibly inspect photo. Verify small/near-limit valid archives and rejection over 28 MiB via TLS; slow/incomplete upload must terminate. Do not weaken limits to pass a test.
9. Restart app then reboot host; prove the exact snapshot/photo bytes survive and same expiry remains. Revoke a token and restart; confirm old token denied and second owner still cannot read/delete first owner's snapshot. Delete and restart; confirm absence. Check timer physically removes synthetic expired records without request traffic using an isolated fixture/drill, never advance production clock or alter real records. Observe cleanup within the healthy-host schedule and alert if no success for 15 minutes.
10. Complete off-site drill below. Retain only sanitized aggregate evidence, checksums, status codes and timestamps. Perform user browser acceptance on phone and desktop. Delete synthetic test data and temporary exports as agreed. Open invitations only after all gates pass and user accepts preview limitations.

## Backup / recovery validation and limits

Local proxy check: run `python3 scripts/check-preview-proxy.py --nginx /absolute/path/to/nginx` with nginx, openssl and Python 3 installed, ports 39300/39443 free. It starts only temporary loopback listeners and removes its certificate/configuration afterward. This checks template syntax and access behavior, not public certificate trust or real-host setup.

Local recovery is tested by npm run test:recovery; that does not prove off-site transport, key retrieval or host recovery. First preview accepts loss of server snapshots on total primary failure, using independently retained tester exports. Do not claim a guaranteed recovery point/time. Proposed drill target: complete the small synthetic restore within one hour and record measured time; no SLA.

Before rollout choose an operator-controlled encrypted off-site destination, jurisdiction, access owner and retention. Proposed synthetic drill backups: one closed-database copy, erase within 24 hours of successful drill and never later than seven days after creation; this does not extend any row's seven-day expiry. No automated backup transport is installed. Scheduled backups and sensitive data remain gated on policy and independent deletion-state design.

Drill steps:
1. Create synthetic retained/deleted/expired fixtures using the existing recovery test methodology. Stop application AND expiry timer/service and confirm all writers stopped. Preserve a closed backup and later latest closed authoritative primary, checksummed, in restricted operator staging. Ordinary copy of a live SQLite file is prohibited.
2. Transfer the encrypted database backup to the approved off-site destination over an authenticated encrypted channel. Record checksum agreement. Keep storage key separately; never include it in the backup archive. Retain current user hashes separately from stale release configuration.
3. Download backup into a new isolated restricted directory on a recovery machine. Retrieve key separately. With all writers stopped and verified latest primary as authority, run npm run storage:recover -- BACKUP NEW_DIRECTORY CURRENT_AUTHORITY. Prove owner/photo bytes and unchanged original expiry; no deleted/expired rows; wrong owner and revoked credentials denied. Never serve raw backup before reconciliation.
4. Repeat in another new isolated destination with --discard-all to represent primary loss. Assert zero restored snapshots; this is the honest disaster-recovery behavior. A stale backup cannot serve as deletion authority. Never claim that transferring two old copies solves this.
5. Record durations/checksums/pass-fail without secrets, remove drill artifacts per agreed policy, and resume service/timer only against approved primary. Provider snapshots, SSD remnants, browser copies and exports are outside database deletion guarantees.

Rollback: block preview access, stop app and timer/service, preserve current closed state, switch only to a schema-compatible previous application release with current credentials/key/database. Never restore an older database to roll back code. On key loss, corruption or uncertain authority, keep access blocked; do not generate a replacement key over existing data.
