# SiteWitness v0.4 — local infrastructure milestone

Date: 2026-11-01. Baseline: `123a06f`.

This milestone does not authorize inference, deployment, billing changes, or infrastructure provisioning. No live model quality or endpoint compatibility is claimed.

## Implemented boundaries

The production analysis handler is locked in code. Setting `INFERENCE_ENABLED=true` alone cannot enable it. Only isolated tests inject authorization and an inference stub. A future live-inference change requires an explicit review and authorization; do not remove this lock as a routine deployment step.

SQLite replaces the process-local request and decode counters. `BEGIN IMMEDIATE` transactions serialize reservations across processes on the same persistent disk. Counters survive handler creation, process restart, and code releases that retain that disk. The shared limits remain 60 attempts/minute and 10 decodes/hour. They do not trust IP headers. Global limits can still be exhausted by another caller.

`INFERENCE_CALL_LIMIT` defaults to zero and caps lifetime inference attempts in that database. Reservations happen before the adapter and are never refunded, including on timeout, failure, or crash. Raising the cap increases the lifetime allowance; restarting does not. This is a call-count ceiling, **not a currency budget**: real pricing, token-cost ceilings, and provider-side spend controls remain unverified. The code lock is the current zero-spend guarantee. Deleting or replacing the database loses counters; backups/restores and rollback to the baseline can weaken controls and need operator review.

## Optional local inspection API

`/api/inspections` is disabled by default and always disabled on Vercel. It supports:

- `POST`: strict JSON `{ "question": "...", "report": { ... } }`, maximum 32 KiB. The report uses the existing validated report schema. Returns a server-generated UUID and expiry. Client-supplied ownership, IDs, photographs, filenames, review fields, and other extra top-level fields are rejected.
- `GET`: returns only the authenticated user's unexpired records, at most 100. These are client-submitted reports, not proof of model generation or professional approval.
- `DELETE ?id=<uuid>`: removes only the caller's own record. Missing and other-owner IDs return the same response.

Use `Authorization: Bearer <token>`. The operator assigns a stable user ID and a unique cryptographically random token of at least 32 bytes, encoded as base64url (43–128 characters). Configuration contains only each token's SHA-256 digest. Never reuse the analysis shared code for these tokens. Authentication does not accept a caller-supplied user ID. Revoke a token by removing its entry; rotate it by changing its hash while retaining the user ID. Duplicate IDs/hashes and malformed configuration fail closed. There is no sign-up, password reset, identity-provider integration, UI login, or automatic browser sync in this milestone.

Records use AES-256-GCM with independent random nonces and authenticated owner/ID/expiry metadata. Encryption protects stored payloads; owner identifiers and counters remain visible to the host operator. A separate server-only 32-byte encryption key is required. Keep it separate from the database. Losing/changing the key makes existing records unreadable; key migration, backup management, and recovery are not implemented. The host operator still has access to data and keys.

Server expiry is seven days after creation, with 100 records/user and 1,000 total. Expired records are hidden and purged on the next list/save operation; there is no background purge while the server is idle. SQLite secure deletion is enabled, but physical media, journals, snapshots, and backups cannot be promised forensic erasure. DELETE affects server records only. Browser-local reports/photos have their original retention behavior, remain unencrypted at application level, and are not migrated, synchronized, or deleted by this API. No original photographs are uploaded to server persistence.

All API responses use `no-store` and `nosniff`. Origin/fetch-site checks supplement bearer authentication. Attempts share a durable 60/minute gate. There are no CORS grants. Use loopback locally and HTTPS with trusted transport/access controls for any future remote single-host installation. Do not use sensitive records until privacy, retention, identity provisioning, and recovery requirements are agreed.

## Local configuration (not activated by this change)

Node 24.x is required for built-in `node:sqlite`; no database package or paid service was added. Use a dedicated absolute `SITEWITNESS_DATA_DIR` outside the repository, public directories, and ephemeral storage, on a trusted persistent local filesystem. The application rejects paths inside the checkout and Vercel use, restricts the data directory to mode 0700 and database to 0600, and rejects a symlink at the data directory/database itself. The operator must ensure trusted ownership and parents; this is not isolation from a compromised host administrator or malicious parent directory.

Set `INSPECTION_STORAGE_ENABLED=true` only for this local API, configure `SITEWITNESS_STORAGE_KEY` as 64 hex characters, and configure `SITEWITNESS_USERS` as a JSON array of `{ "id": "stable-user-id", "tokenHash": "64-lowercase-hex-digest" }`. Example configuration contains placeholders only. Do not commit keys, tokens, databases, or backups. Leave inference disabled and the call allowance zero. No real user credentials or persistent database were created during development; tests use temporary synthetic data and clean up.

Storage errors, malformed configuration, contention, and missing storage fail closed. No in-memory fallback exists. SQLite is synchronous and appropriate only for this bounded, single-host milestone; high-volume operation, multiple hosts, distributed rate limiting, and database migrations are not validated.

## Vercel preview readiness and remaining blockers

The preview configuration explicitly disables inference and server storage, sets call allowance zero, and sends a `noindex, nofollow` header. This header is not access control. Keep preview deployment access restricted through the selected account's available controls and verify their availability/cost before any authorized deployment. No Vercel CLI action or cloud configuration was performed.

Vercel functions have ephemeral storage, so this SQLite implementation is deliberately rejected there. A shared durable service with atomic operations and an agreed no-cost plan would be required for hosted persistence and usage accounting. No service was provisioned and no free-tier availability or future cost is assumed. Reference: [Vercel SQLite support](https://vercel.com/kb/guide/is-sqlite-supported-in-vercel).

The existing 4 MiB image cap plus 64 KiB multipart overhead remains below the documented 4.5 MB function payload limit; platform errors may still be non-JSON and the UI handles that. Confirm the target account supports Node 24 and the configured 60-second analysis duration before deployment. References: [Node runtime](https://vercel.com/docs/functions/runtimes/node-js), [function limits](https://vercel.com/docs/functions/limitations), [Node 24 SQLite](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html).

An authorized preview can demonstrate the existing browser-local workspace and disabled API boundaries. It cannot demonstrate live inference or cross-device persistence. Real model evaluation, SAM integration, distributed storage/authentication, monetary budgets, retention policy approval, and deployment smoke tests remain outstanding.
